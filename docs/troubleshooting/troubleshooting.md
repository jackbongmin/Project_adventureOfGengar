## 1. 캐릭터가 화면에서 어긋나서 코인이 안 먹어지고 구덩이에 빠짐

**증상**
스크롤이 진행될수록 화면에 보이는 캐릭터 위치와 실제 충돌 위치가 달라졌다. 점프할 때 코인이 안 먹어지고, 평지에 서 있다고 생각했는데 갑자기 구덩이로 떨어졌다. 같은 코드인데 보스전(카메라가 고정된 맵)에서는 멀쩡해서 더 헷갈렸다.

**원인**
적, 코인, 타일은 `x - cam.x`로 화면 좌표로 바꿔서 그렸는데, **플레이어만 월드 좌표 그대로** 그리고 있었다. 카메라가 오른쪽으로 갈수록 그림과 판정이 벌어졌다. 보스전은 카메라가 0에 고정이라 오차가 없었던 것이다.

**해결**
```js
// 전: drawPhantom(P.x + P.w / 2, ...)
drawPhantom(P.x + P.w / 2 - cam.x, ...)
```

**배운 점**
월드→화면 좌표 변환을 그리는 곳마다 따로 하면 하나쯤은 빠뜨린다. C++로 옮길 때는 `Graphics::SetOffset(카메라 + 흔들림)`을 한 곳에서만 적용하고, 액터는 **월드 좌표로만** 그리도록 바꿨다. 이제는 액터 쪽에서 카메라를 신경 쓸 일이 없다.

## 2. Alt 키 입력이 자꾸 씹힘

**증상**
점프를 Alt로, 공격을 Ctrl로 잡았는데 Alt가 자주 안 먹었다.

**원인**
정확한 내부 동작까지는 못 찾았다. 다만 Alt는 브라우저/OS가 메뉴 포커스 같은 용도로 먼저 가져가는 키이고, Ctrl은 Ctrl+R(새로고침), Ctrl+W(탭 닫기) 같은 단축키와 겹친다. 게임 키로 쓰기에 애초에 좋은 선택이 아니었다.

**해결**
점프 `C`, 공격 `Z`, 필살기 `X`로 바꿨다(Space와 ↑도 점프로 허용). 키를 바꿀 때 코드를 여기저기 고치지 않도록, 키 배치를 `Input.cpp`의 **액션별 바인딩 표** 한 곳으로 모았다.

**배운 점**
브라우저에서 돌아가는 게임은 Alt, Ctrl, F5 같은 브라우저 예약 키를 피한다. 키 입력은 "어떤 키"가 아니라 "어떤 동작(Action)"으로 추상화해 두면 이런 변경이 쉽다.

## 3. emsdk 설치가 exit code 49로 실패

**증상**
```
emsdk install latest
Python Python
(exit code 49)
```
`emsdk.bat`도 `emsdk.ps1`도 똑같이 실패했다.

**원인**
이 PC의 `python.exe`가 진짜 Python이 아니라 **Microsoft Store 실행 스텁**이었다. emsdk는 시스템 Python으로 자기 자신(`emsdk.py`)을 실행하는데, 스텁이라 아무것도 실행되지 않았다.

**해결 과정**
1. emsdk가 쓰는 번들 Python(`python-3.13.3-0-win-amd64.zip`, 약 28MB)을 받아서 `C:\emsdk\python\3.13.3_64bit`에 풀었다. → `emsdk.ps1`이 이 경로를 먼저 찾는다.
2. 다시 `install latest`를 돌리자 이번에는 `Permission denied: ...\DLLs\libcrypto-3.dll`로 실패했다. emsdk가 설치 단계에서 **같은 경로에 Python을 다시 풀려고** 하는데, 그 Python이 지금 실행 중이라 DLL이 잠겨 있었다.
3. 번들 Python을 `C:\emsdk\python-bootstrap`으로 **옮겨서** 그걸로 `emsdk.py`를 직접 실행했다.
```powershell
C:\emsdk\python-bootstrap\python.exe C:\emsdk\emsdk.py install latest
C:\emsdk\python-bootstrap\python.exe C:\emsdk\emsdk.py activate latest
```
설치가 끝난 뒤에는 `python-bootstrap`을 지웠다.

**배운 점**
"설치 도구를 돌리는 인터프리터"와 "설치 대상 폴더"가 같으면 파일 잠금에 걸린다. 가장 간단한 우회는 시스템에 진짜 Python을 설치하는 것이다. 설치 후에는 `emcc --version`으로 동작을 확인했다.

## 4. 링크 에러: `__cxa_pure_virtual`, `operator new`

**증상**
컴파일은 전부 통과하는데 링크에서 수십 줄이 쏟아졌다.
```
wasm-ld: error: ...: undefined symbol: __cxa_pure_virtual
wasm-ld: error: ...: undefined symbol: operator new(unsigned long)
emcc: warning: link failed with undefined C++ symbols. Try linking with 'em++' or passing '-sDEFAULT_TO_CXX'
```

**원인**
C++ 프로젝트인데 링크를 `emcc`로 했다. `emcc`는 C++ 표준 라이브러리(`new`, 예외, RTTI 등)를 자동으로 링크하지 않는다.

**해결**
빌드 스크립트의 `emcc`를 `em++`로 바꿨다. 경고 메시지가 해결책을 그대로 알려 주고 있었다.

**배운 점**
`g++`와 `gcc`의 차이와 같다. C++ 소스는 처음부터 `em++`로 빌드한다.

## 5. PowerShell 빌드 스크립트가 이상하게 동작

두 가지를 연달아 만났다.

### 5-1. `emcc: error: O: No such file or directory`

**증상**
옵션 `-O2`를 넘겼는데 `O`라는 이름의 입력 파일을 찾는다는 에러가 났다.

**원인**
```powershell
$opt = if ($Debug) { @("-O0", "-g") } else { @("-O2") }
& em++ @sources ... @opt
```
`if` 식의 결과가 원소 1개짜리 배열이면 PowerShell이 **문자열로 풀어 버린다.** 그 문자열 `"-O2"`를 `@opt`로 스플랫하면 `-`, `O`, `2`처럼 **글자 단위 인자**로 쪼개졌다.

**해결**
```powershell
$opt = @("-O2")
if ($Debug) { $opt = @("-O0", "-g") }
```

### 5-2. emsdk 환경 설정에서 스크립트가 중단됨

**증상**
`emsdk_env.ps1`을 호출하면 `NativeCommandError`로 스크립트가 멈췄다.

**원인**
emsdk가 "Setting up EMSDK environment" 같은 **안내 메시지를 stderr로 출력**한다. 내 스크립트가 `$ErrorActionPreference = "Stop"`이어서 이걸 에러로 받아들였다. (Windows PowerShell 5.1에서 네이티브 명령의 stderr 처리 방식 때문이다.)

**해결**
`EMSDK_QUIET=1`을 주고, `$ErrorActionPreference = "Continue"`로 두었다. 성공 여부는 메시지가 아니라 **종료 코드**(`$LASTEXITCODE`)로 판단한다.

**배운 점**
PowerShell은 "원소 하나짜리 배열"과 "stderr 출력"이 쉘과 다르게 동작한다. 스크립트는 작게 쪼개서 바로 돌려 보는 게 빠르다.

## 6. 컴파일 에러: 멤버 함수가 같은 이름의 전역 함수를 가림

**증상**
```
Boss.cpp:43:17: error: too many arguments to function call, expected 0, have 1
    attackName_ = AttackName(attack);
```

**원인**
`Boss` 클래스에 `const char* AttackName() const`라는 멤버 함수가 있고, 전역에는 `AttackName(BossAttack)`이 따로 있었다. 클래스 안에서 `AttackName(...)`을 부르면 컴파일러가 **멤버 함수 이름을 먼저 찾고, 같은 이름의 바깥 함수는 후보에서 제외한다** (name hiding). 멤버 쪽은 인자가 없으니 "인자가 너무 많다"고 한 것이다.

**해결**
전역 함수를 명시해서 호출했다.
```cpp
attackName_ = gengar::AttackName(attack);
```

**배운 점**
Java는 오버로드가 클래스 안에서만 해석되지만, C++는 **이름 탐색이 안쪽 스코프에서 끝난다.** 멤버 이름과 전역 함수 이름이 같으면 이런 일이 생기니 이름을 겹치지 않게 짓는 게 제일 낫다.

## 7. `index.html`을 열어도 안 되고, 실행 명령도 에러가 남

### 7-1. 더블클릭하면 아무것도 안 뜸
**원인**
브라우저는 `file://`로 연 페이지에서 `.wasm`을 `fetch`하는 것을 막는다.

**해결**
로컬 서버가 필요하다. `emrun`으로 서버를 띄우는 `scripts/run_web.ps1`을 만들었다. 직접 서버를 만들 때는 `.wasm`을 `application/wasm` MIME으로 내려줘야 한다. (확장자 기본 MIME으로 내려가면 스트리밍 컴파일이 실패한다.)

### 7-2. `-File 매개 변수에 대한 인수 'scripts\run_web.ps1'이(가) 없습니다`
**원인**
터미널의 현재 폴더가 `C:\Users\user`였다. `-File`에 준 `scripts\run_web.ps1`은 **현재 폴더 기준 상대 경로**라 못 찾았다. 스크립트 내부는 자기 위치(`$PSScriptRoot`) 기준으로 경로를 계산하므로 문제가 없었고, 실행하는 쪽의 문제였다.

**해결**
프로젝트 폴더로 이동한 뒤 실행하거나 전체 경로를 준다. README에 "프로젝트 폴더로 이동한 뒤 실행"을 적어 두었다.

## 8. 늑대가 위 발판에 있는 나를 계속 타겟으로 잡음

**증상**
내가 위쪽 블록에 올라가 있는데도 늑대가 타겟을 안 풀고 바로 아래에서 대기했다. 한 번 올라갔다가 내려오려면 늑대가 기다리고 있어서 까다로웠다.

**원인**
추적 조건이 거의 가로 거리 위주였다. 시작 조건의 세로 허용치가 110px, 포기 조건이 220px라서, 낮은 발판(세로 차이 약 99px) 위의 플레이어는 시작도 되고 포기도 안 됐다.

**해결**
- 추적 **시작**은 높이 차이 70px 이내로 제한 (같은 높이일 때만).
- 추적 중에 높이 차이가 90px를 넘는 상태가 **1초(60프레임) 이상** 이어지면 포기하고 순찰로 복귀.
- 포기한 뒤 **2.5초 동안은 다시 잡지 않음.** 그러지 않으면 포기하자마자 바로 다시 잡을 수 있다.

점프는 순간적으로 높이 차이가 커졌다가 돌아오므로 "시간 조건"을 두면 자연스럽게 무시된다.

**어떻게 검증했나**
이 상황을 손으로 만들기가 번거로워서 `heightdemo=1` 옵션을 만들었다. 플레이어를 위 발판에 올리고, 아래에 이미 추적 중인 늑대를 두는 시나리오다. 로그에 `alerted (forced) dy=-99` 다음 `gave up (target on a different height)`가 찍히고, 이후 다시 잡지 않는 것을 확인했다. 같은 높이에서는 원래대로 추적하는지도 봇 플레이 로그로 같이 봤다.

**배운 점**
AI 상태(추적/포기)에는 **히스테리시스**(시작 기준과 포기 기준을 다르게)와 **시간 조건**, **쿨다운**이 필요하다. 순간값만 보면 경계에서 계속 들락거린다.

## 9. 늑대가 순찰 중에 앞이 아니라 나를 바라보며 움직임

**증상**
추적이 풀린 늑대가 걸어 다니는데, 진행 방향이 아니라 **계속 나를 바라보면서** 옆걸음 치듯 움직였다.

**원인**
방향을 갱신하는 코드가 이랬다.
```cpp
if (intent_.moveX != 0.f) SetFacing(static_cast<int>(intent_.moveX));
```
순찰 속도는 추적 속도의 비율(`0.7 / 2.1 ≈ 0.33`)로 `moveX`에 들어간다. `static_cast<int>(0.33f)`는 **0**이다. 그래서 `SetFacing(0)`이 되어 방향이 갱신되지 않았고, 추적할 때 나를 보던 방향이 그대로 남았다. 슬라임은 `moveX`가 ±1이라 멀쩡했고, 소수 값을 쓰는 늑대만 걸렸다.

**해결**
부호만 필요하니 `Sign()`으로 바꿨다. 플레이어 쪽의 같은 코드도 함께 바꿨다.
```cpp
if (intent_.moveX != 0.f) SetFacing(Sign(intent_.moveX));
```

**어떻게 검증했나**
고치기 전에 먼저 **재현**부터 했다. 늑대의 컨트롤러에 "직전에 가려던 방향과 지금 바라보는 방향이 다르면 로그를 남기는 검사"를 넣고 돌리자, 고치기 전에는 이렇게 찍혔다.
```
[hound] FACING MISMATCH: moving left but facing right (aggro=0)
```
수정 후에는 같은 시나리오 20초와 전체 플레이에서 한 번도 안 찍혔다. 이 검사는 `log=1`일 때만 동작하게 남겨 뒀다.

**배운 점**
`float`를 `int`로 캐스트하면 소수점이 **0 방향으로 버려진다.** 방향이 필요하면 `Sign()`을 쓴다. 고치기 전에 버그를 재현하는 검사를 먼저 넣으면 "진짜 고쳐졌는지"를 확인할 수 있다.

## 10. 보스가 계속 따라다니면서 몸통 피해를 너무 많이 줌

**증상**
보스가 나를 계속 쫓아와서 몸통으로 피해를 줬다. 멀리서 쏘는 패턴이나, 준비 동작을 보여 주고 달려드는 패턴이 있었으면 좋겠다고 느꼈다.

**원인**
- 보스가 플레이어 근처로 계속 붙는 이동이었다.
- 보스 몸통의 접촉 피해가 **항상** 켜져 있었다.

**해결**
- 평소에는 플레이어와 **약 230px 거리를 유지**하며 떠 있고, 벽에 몰리면 반대편으로 넘어간다.
- 접촉 피해(`contactEnabled`)는 **몸으로 덮치는 기술** (바닥 질주, 내려찍기 낙하, 돌격)을 쓰는 동안에만 켠다.
- 원거리 패턴(소용돌이 탄막, 유도탄)과 "조준선으로 위치를 고정해 보여 준 뒤 돌진하는 **돌격**"을 추가했다. 패턴은 총 12개가 됐다.

**어떻게 검증했나**
`bossphase`, `immortal` 옵션으로 단계별로 보스를 불사 상태에서 돌리고, 패턴이 순서대로 나오는지와 피격 출처(`orb`, `pillar`, `beam`, `shockwave`, `boss-body`)를 로그로 셌다. 몸통 접촉 피해는 이전 수백 번에서 1~2번으로 줄었다.

**배운 점**
"피해를 주는 조건"을 객체에 상시 켜 두지 말고, **상태(State)에 묶어서** 켜고 끄면 설계가 깔끔하다. 보스를 상태 머신으로 만든 덕분에 가능했다.

---

## 11. 업그레이드하면 보스가 순식간에 녹아서 패턴을 못 봄

**증상**
연사 속도, 공격력, 투사체 수를 올리면 보스가 금방 죽어서 패턴을 제대로 볼 수 없었다.

**원인**
세 업그레이드가 **곱해진다.** 대략 이렇게 계산된다.
- 연사 간격 24프레임 → 최대 9프레임 (약 6.7발/초)
- 발사 수 1 → 3
- 공격력 1 → 5

전부 올리면 이론상 초당 100 가까이 들어간다. 보스 체력 150으로는 몇 초면 끝이다.

**해결**
- 기본 체력을 150 → **300**으로 올렸다.
- 위력/연사/다중 발사 업그레이드 레벨 합계에 **비례해서 보스 체력이 늘어나게** 했다. (레벨 1당 +12%)
- 보스 수치(이동 속도, 쉬는 시간, 패턴별 탄 수/속도/예고 시간)는 코드 여기저기에 흩어져 있어서 조정하기 힘들었다. 단계별 **난이도 표(`BossTuning.cpp`)** 한 곳으로 모았다.

**결과**
자동 플레이로 확인했을 때 업그레이드한 상태에서 전투가 약 70초 지속됐다.

**배운 점**
곱셈으로 쌓이는 성장 요소는 밸런스가 한쪽으로 쏠리기 쉽다. 상대 체력을 플레이어 성장에 연동하거나, 수치를 표로 빼 두면 조정이 빨라진다.

## 12. 상점 항목 이름이 직관적이지 않음

**증상**
`SHADOW POWER`, `VOID BURST`, `SWIFT STEP` 같은 이름만 봐서는 사면 무엇이 좋아지는지 알기 어려웠다.

**해결**
- 이름을 `ATTACK POWER`, `FIRE RATE`, `MOVE SPEED`, `ULTIMATE POWER`처럼 바로 이해되는 말로 바꿨다.
- 선택한 항목을 사면 **무엇이 얼마로 바뀌는지** 화면에 미리 보여 준다. (`BALLS PER SHOT 1 -> 2`, `ATTACK DAMAGE 2 -> 3`)
  미리보기는 실제 능력치 계산식(`PlayerStats.h`)을 한 단계 올린 세션 복사본에 적용해서 구한다. 그래서 수식을 바꿔도 미리보기가 따로 어긋나지 않는다.

## 13. 풀피인데 하트를 먹어서 아까움

**증상**
체력이 가득 찼는데 하트를 밟으면 그냥 사라졌다.

**해결**
체력이 가득 차 있으면 하트가 먹어지지 않고 **그 자리에 남도록** 했다. 나중에 다친 뒤 돌아와서 먹을 수 있다.

**어떻게 검증했나**
`heartdemo=1`로 시작 지점에 하트를 놓고 두 경우를 돌렸다. 풀피일 때는 `left in place (full hp 3/3)`, `hp=1`로 시작하면 `collected (hp 1 -> 2)`가 찍혔다.

## 14. 단일 HTML로 묶을 때 NUL 문자 경고

**증상**
wasm까지 한 파일에 넣은 HTML(`-sSINGLE_FILE=1`)을 올리자 "line 38에 NUL(`\u0000`) 바이트가 있다"는 경고가 떴다.

**원인**
이 Emscripten 버전은 `SINGLE_FILE`일 때 wasm을 **이진 문자열**로 JS에 박는다. 그 안에 NUL 문자가 대량으로 들어 있어서, 브라우저가 HTML을 파싱하면서 이를 `U+FFFD`로 바꿔 wasm이 깨질 수 있다.

**해결**
```
-sSINGLE_FILE=1 -sSINGLE_FILE_BINARY_ENCODE=0
```
이진 문자열 대신 **base64**로 넣는다. 용량은 약 17% 늘지만 순수 ASCII다. 결과 파일의 바이트를 검사해서 NUL 0개, 비ASCII 0개인 것을 확인했다.

## 15. 자동 테스트가 너무 느리거나 입력이 뭉침

**증상**
- 자동 플레이(`bot=1&speed=16`)를 돌려도 한참 지나야 스테이지 1에 머물러 있었다.
- 키 입력을 합성해서 상점을 조작했는데 일부 입력이 사라진 것처럼 보였다.

**원인과 해결**
1. 브라우저 탭이 **백그라운드**면 `requestAnimationFrame`이 초당 1~3프레임으로 떨어진다. 게임 로직은 프레임마다 고정 스텝을 몰아서 돌리므로(`speed` 배율에도 한계가 있다) 진행이 거의 멈췄다. → 탭을 앞으로 가져오니 바로 끝났다.
2. 프레임이 느리면 짧은 간격으로 보낸 키 입력이 **한 프레임에 합쳐진다.** 입력 사이에 충분한 대기 시간을 두었다.
3. 입력이 사라진 것처럼 보였던 건 사실 내 착각이었다. `shop=1` 옵션은 **타이틀에서 Enter를 눌러야** 적용되는데, 그 Enter를 상점 조작으로 셌다. 게임 문제가 아니었다. 이벤트 로그를 찍어 보고 알았다.

**배운 점**
검증 결과가 이상하면 게임 코드보다 **검증 방법**부터 의심한다. 로그를 남겨 두면 어디서 틀렸는지가 바로 보인다.

## 16. 몬스터를 밟았는데 거의 매번 내가 데미지를 받음

**증상**
위에서 몬스터를 밟으면 가끔은 멀쩡했지만, 대부분은 밟는 순간 내 하트가 깎였다. 특히 늑대나 스테이지 2 이후의 적을 밟을 때 심했다.

**원인**
적은 매 프레임 "플레이어 박스와 겹쳤나?"만 보고, 겹쳤으면 그 자리에서 밟기인지 몸통 접촉인지 고른다. 밟기 조건은 `떨어지는 중(vel.y > 1)` + `발이 머리 안으로 18px 미만 들어옴`이었다. 여기에 구멍이 두 개 있었다.

1. **밟은 다음 프레임에도 아직 겹쳐 있다.** 밟기 피해는 2인데 적 체력은 슬라임 `2 + 스테이지`, 늑대 `3 + 스테이지`라서 1스테이지 슬라임 말고는 한 번에 안 죽는다. 플레이어는 `-8.5`로 튕기지만, 다음 프레임에 올라가는 거리는 중력 때문에 약 8px뿐이다. 그런데 밟은 순간 이미 최대 12px(낙하 속도)까지 파고들어 있을 수 있어서, 8px 넘게 파고든 경우엔 **다음 프레임에도 겹쳐 있다.** 그때는 이미 위로 올라가는 중(`vel.y < 0`)이라 밟기 조건에서 떨어지고, 그대로 **몸통 접촉 피해**가 들어갔다.
   → "가끔 멀쩡했던" 경우는 적이 한 번에 죽었거나(1스테이지 슬라임) 우연히 얕게 파고든 경우였다.
2. **파고든 깊이로 위/옆을 가렸다.** 늑대가 점프해 올라오는 순간 밟으면 서로 다가오는 속도가 `12 + 9.5`가 되어 한 프레임에 18px를 넘게 파고든다. 분명히 위에서 밟았는데도 옆에서 부딪힌 것으로 처리됐다.

**해결** (`Enemy::ContactPlayer`)
- 밟기는 겹친 깊이 대신 **직전 프레임 위치**로 판정한다. 직전 프레임에 플레이어 발(`발 - vel.y`)이 적 머리(`머리 - 적 vel.y`)보다 위(여유 6px)에 있었고, 적보다 빠르게 내려오고 있었으면 밟기다.
- 밟힌 적은 **12프레임 동안 그 플레이어에게 몸통 피해를 주지 않는다.** 아직 겹쳐 있으면 떨어질 때까지 유예를 늘린다. (점프 중인 늑대가 튕겨 오르는 나를 따라 올라오는 경우)
```cpp
const float prevFeet = p.Bounds().Bottom() - p.vel.y;
const float prevHead = pos.y - vel.y;
if (p.vel.y > vel.y && prevFeet <= prevHead + kStompSlack) {  // 밟기
  stompGrace_ = kStompGraceFrames;
  ...
```

**다른 방법도 생각했다**
"밟기용 박스를 몸통 박스보다 위에 따로 두자"는 방법도 있었다. 하지만 이건 2번(빠르게 파고들기)만 줄여 줄 뿐, 1번(밟은 다음 프레임에 몸통과 겹침)은 그대로 남는다. 판정 박스를 키우면 옆에서 닿았는데 밟기가 되는 경우도 생긴다. 그래서 박스는 그대로 두고 "어디서 왔는가"와 "방금 밟혔는가"를 보도록 바꿨다.

**어떻게 검증했나**
- `stompdemo=N` 옵션을 추가했다. 가만히 선 늑대 머리 위에서 플레이어를 떨어뜨리고, N(1~32)만큼 시작 높이를 1px씩 바꿔 파고드는 깊이를 달리한다. `log=1`과 같이 켜면 `[enemy] stomped (depth ..)` / `[enemy] body contact (..)` 로그가 남는다.
- 게임과 같은 수치(중력 0.55, 최대 낙하 12, 반동 -8.5, 히트스톱 2프레임)로 판정만 따로 시뮬레이션했다.

| 상황 (각 200가지) | 수정 전 피격 | 수정 후 피격 |
|---|---|---|
| 가만히 선 늑대를 여러 높이에서 밟기 | 51 | 0 |
| 점프 중인 늑대를 여러 타이밍에 밟기 | 165 | 0 |

옆에서 부딪히는 경우는 전과 똑같이 피해를 받는다. 데모 중 서 있는 나에게 슬라임이 걸어와 부딪힌 로그가 `body contact (depth 22.0, player vy 0.0)`이었는데, 새 판정에서도 `vel.y`가 둘 다 0이라 밟기 조건(`p.vel.y > vel.y`)에 들지 않는다.

**배운 점**
충돌을 "지금 겹쳤는가" 한 장면만 보고 판정하면, 한 프레임에 많이 움직이는 순간과 **판정 직후의 프레임**이 빠진다. 방향이 중요한 판정(밟기, 일방통행 발판)은 직전 프레임 위치를 같이 본다. 공중 발판도 같은 이유로 `prevBottom`을 쓰고 있었다.

## 정리: 디버그 옵션을 만들어 두길 잘한 이유

문제 대부분을 "사람이 직접 해 보기"로 재현하려면 시간이 너무 오래 걸렸다. 그래서 다음을 만들어 두었다.

- `bot=1` 자동 플레이 봇, `god=1` 무적, `speed=N` 배속
- `log=1` 이벤트 로그 (스테이지, 상점, 보스 패턴, 피격 출처)
- `stage`, `coins`, `hp`, `bossphase`, `immortal`, `heightdemo`, `heartdemo`, `stompdemo` 같은 상황 재현 옵션

옵션 목록은 [README](../../README.md)에 있다. 버그를 고치기 전에 **재현하는 로그를 먼저** 넣고, 고친 뒤 같은 시나리오로 다시 돌려서 확인하는 방식이 가장 확실했다.
